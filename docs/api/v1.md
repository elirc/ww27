# Customer Profiles API v1

Source of truth:
- Registry: `src/lib/versioning/version-registry.ts` (`versionRegistry.v1`, lines 15-32)
- Schemas: `src/lib/validation/customer-profile-schemas.ts` (`createProfileV1Schema` 18-23, `updateProfileV1Schema` 25)
- Mappers: `src/lib/versioning/customer-profile-contracts.ts`
- Routes: `src/app/api/platform/customer-profiles/route.ts` and `src/app/api/platform/customer-profiles/[profileId]/route.ts`

Lifecycle (from the registry):
- Status: `DEPRECATED`
- Default version: `true`. A request that names no version gets v1 (`getDefaultVersion`, registry lines 61-69).
- Deprecation date: `2026-02-01`. This is stored in the registry but **not** emitted in any header.
- Sunset: `2026-12-31`
- Rollout: 100 %, empty allow-list

## Selecting v1

`getRequestedVersion` (`src/lib/http/api-context.ts:26-43`) chooses the version in this order:

1. an explicit argument
2. the `x-api-version` header
3. the `?version=` query parameter
4. the default (v1)

An unknown value throws `badRequest`. Every request also needs the demo session headers `x-user-id`, `x-user-role` (`ADMIN`, `SUPPORT`, `ANALYST`, or `CLIENT`), and `x-client-id`. Without them the response is 401 (`src/lib/auth/session.ts:19-38`).

## Request shapes

Create (`POST /api/platform/customer-profiles`), strict, so extra keys are rejected:

```json
{
  "externalReference": "acct_legacy",
  "fullName": "Ada Lovelace",
  "email": "ada@example.com",
  "status": "active"
}
```

- `externalReference`: 3-50 characters. `fullName`: 3-120 characters. `email`: a valid email. `status`: `active` or `inactive`.
- Update (`PATCH .../{profileId}`): the same fields, all optional, still strict.

## Response shape

```json
{
  "id": "profile_123",
  "externalReference": "acct_legacy",
  "fullName": "Ada Lovelace",
  "email": "ada@example.com",
  "status": "active",
  "createdAt": "2026-04-13T00:00:00.000Z"
}
```

The body is wrapped in `{ "profile": ... }` for single-item responses and `{ "profiles": [...] }` for lists.

## Mapping rules (lossy by design)

`toCanonicalCreateInput` and `toCanonicalUpdateInput` (`customer-profile-contracts.ts:103-155`) translate v1 into the canonical model:

| v1 field | Canonical | Notes |
|---|---|---|
| `fullName` | `givenName` = first whitespace-separated word; `familyName` = the rest | `splitFullName` (86-93). A single-word name stores `familyName: "Unknown"` |
| `status: "active"` | `lifecycleState: "ACTIVE"` | `fromLegacyStatus` (99-101) |
| `status: "inactive"` | `lifecycleState: "SUSPENDED"` | |
| (absent) | `marketingOptIn: false` on create | v1 cannot express it. Updates leave it untouched |

On the way out, `toVersionedCustomerProfile` (169-183) joins `givenName` and `familyName` with a space and maps `ACTIVE` and `TRIAL` to `active`, and `SUSPENDED` and `ARCHIVED` to `inactive` (`toLegacyStatus`, 95-97).

Consequences a v1 client should know:

- A profile created with `fullName: "Ada"` comes back as `"Ada Unknown"`.
- A `TRIAL` profile reads as `active`. If a v1 client PATCHes `status: "active"` back, the profile becomes `ACTIVE`, so the trial state is lost.
- An `ARCHIVED` profile reads as `inactive`. A v1 PATCH to `active` is refused with 409 by the service (`src/services/customer-profile-service.ts:33-35`).

## Headers

`jsonWithVersionHeaders()` (`src/lib/http/api-response.ts:17-41`) sets these on every v1 response, **including error responses**, because `toErrorResponse` uses the same helper (`src/lib/http/route-utils.ts:21-54`):

- `x-api-version: v1`
- `x-api-lifecycle: DEPRECATED`
- `Deprecation: true`
- `Warning: 299 - "v1 is deprecated and will sunset on 2026-12-31"`
- `Sunset: 2026-12-31`

The `Sunset` value is a bare date. RFC 8594 specifies an HTTP-date, for example `Thu, 31 Dec 2026 00:00:00 GMT`. Clients that parse it strictly may ignore it.

## Usage metrics

Every response, success or failure, is recorded through `recordVersionUsage` (`route-utils.ts:56-71`) with `deprecationFired: true` for v1. Use these rows to find remaining v1 callers before the sunset date.
