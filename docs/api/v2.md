# Customer Profiles API v2

Source of truth:
- Registry: `src/lib/versioning/version-registry.ts` (`versionRegistry.v2`, lines 33-48)
- Schemas: `src/lib/validation/customer-profile-schemas.ts` (`createProfileV2Schema` 27-36, `updateProfileV2Schema` 38)
- Mappers: `src/lib/versioning/customer-profile-contracts.ts`
- Routes: `src/app/api/platform/customer-profiles/route.ts` and `src/app/api/platform/customer-profiles/[profileId]/route.ts`

Lifecycle:
- Status: `CURRENT`
- Default version: `false`. Clients must ask for v2 explicitly, with `x-api-version: v2` or `?version=v2`.
- Static rollout in the registry: 40 %, allow-list `["beta-client", "internal-admin"]`
- Runtime rollout is controlled by `updateRollout()` in `src/services/api-version-service.ts` (lines 107-143). `getEffectiveVersionDefinition` (92-105) applies the stored override, when one exists, on every request.

## Who can call v2

`assertVersionAccess` (`src/lib/versioning/version-rollout.ts:19-34`) runs inside `buildApiContext`, before any route logic:

1. `ADMIN`, `SUPPORT`, and `ANALYST` sessions always pass.
2. A `CLIENT` whose `x-client-id` is on the allow-list passes.
3. Otherwise `stableBucket(clientId) < percentage` must hold. The bucket is the sum of the client id's character codes, mod 100 (line 16).
4. Anyone else gets 403 `Version v2 is not rolled out to client ...`.

Two caveats:

- The bucket function is deterministic but crude. Ids made of the same characters always land in the same bucket.
- `x-client-id` is a caller-supplied header in this demo (`src/lib/auth/session.ts:22`). Any caller can pick an allow-listed id. The rollout gate is a traffic-shaping tool, not an access control.

## Request shapes

Create, strict:

```json
{
  "externalReference": "acct_modern",
  "name": { "givenName": "Ada", "familyName": "Lovelace" },
  "email": "ada@example.com",
  "lifecycleState": "ACTIVE",
  "marketingOptIn": true
}
```

- `name.givenName` and `name.familyName`: 2-60 characters each (the inner object is also strict).
- `lifecycleState`: `TRIAL`, `ACTIVE`, `SUSPENDED`, or `ARCHIVED`.
- `marketingOptIn`: a boolean.
- Update: every field optional, still strict. `name`, if present, must contain both parts.

## Response shape

```json
{
  "id": "profile_123",
  "externalReference": "acct_modern",
  "name": {
    "givenName": "Ada",
    "familyName": "Lovelace"
  },
  "email": "ada@example.com",
  "lifecycleState": "ACTIVE",
  "marketingOptIn": true,
  "createdAt": "2026-04-13T00:00:00.000Z"
}
```

## Compatibility rules

- `toCanonicalCreateInput()` and `toCanonicalUpdateInput()` in `src/lib/versioning/customer-profile-contracts.ts` keep the service layer version-agnostic. The v2 update mapper copies only the fields that are present (lines 156-166), so `marketingOptIn: false` is preserved and omitted fields are not padded with `undefined`.
- `assertVersionAccess()` in `src/lib/versioning/version-rollout.ts` enforces the percentage rollout and the allow-lists before the route reaches business logic.
- `getCreateProfileSchema("v2")` in `src/lib/validation/customer-profile-schemas.ts` is strict, so extra fields cannot silently drift into the contract.
- The service rejects any transition **out of** `ARCHIVED` with 409 (`src/services/customer-profile-service.ts:24-36`). Transitions between the other states are unrestricted.

## Headers

`x-api-version: v2` and `x-api-lifecycle: CURRENT`. There are no deprecation or sunset headers, because v2 has no `sunsetDate` (`src/lib/http/api-response.ts:25-38`).

## Known edge case

Requesting an unsupported version, for example `x-api-version: v9`, throws `badRequest` inside `buildApiContext`. Each route's `catch` block then calls `getRequestedVersion(request)` **again** to choose headers for the error response (for example `customer-profiles/route.ts:58`). That second call throws the same error outside any `try`. The caller therefore gets the framework's generic 500 instead of the intended 400. Reading the code shows this. It has not been reproduced.
